# Deep-Custom AI Knowledge Base Designer — 产品规格书

> 版本：v1.0 | 日期：2026-05-04 | 状态：当前阶段唯一产品方向
>
> **Working Backwards from the Customer**：本文档从 deep-custom 用户的实际需求出发，定义什么是"好的知识库系统"，再推导需要构建什么。在 PR/FAQ 通过之前，不分配实现资源。

---

## 0. 产品一句话

**先通过深度诊断理解用户，再为用户生成专属知识库结构、分类规则、报告模板、检索策略和自动整理流程。**

这个系统不是通用知识库软件，它是 Personal Knowledge Infrastructure Generator —— 每个用户得到的是一套**为自己量身定制的知识管理系统**，包括分类体系、标签策略、报告模板、检索优先级、整理节奏。

---

## 1. 产品定位

### 1.1 我们是什么

**AI Knowledge Base Designer**：一个诊断-设计-生成系统。输入是用户的文件系统和回答，输出是一套完整的、可运行的、为该用户定制的知识库基础设施。

**Personal Knowledge Infrastructure Generator**：生成的不只是"分类建议"，而是一个可运行的配置包——分类规则、标签体系、检索策略、报告模板、自动整理流程——全部由 AI 根据对用户知识资产的深度理解而生成。

### 1.2 我们不是什么

| 不是 | 为什么 |
|------|--------|
| ~~普通知识库软件~~ | 用户不需要又一个 Obsidian / Notion / Logseq。这些工具给的是空白画布，用户要的是**画好的画**。 |
| ~~文件搜索工具~~ | 搜索是基础设施，不是产品。用户要的不是"找到文件"，是"理解自己知道什么、缺什么、想什么"。 |
| ~~模板市场~~ | 模板是预先做好的通用结构。deep-custom 的反面——我们不做"选一个模板套上去"，我们做"从零分析你的文件，生成只属于你的结构"。 |
| ~~多用户平台~~ | 当前阶段只服务一个深度用户。多人协作、共享知识库、团队定价——这些会稀释 deep-custom 的核心价值。 |
| ~~MCP 商业化~~ | MCP 是对外集成的协议，不是产品。 |
| ~~quick-start / guided-custom / 浅层问卷~~ | 这些是"让用户 5 分钟上手"的设计思路。deep-custom 用户愿意花时间做深度诊断，因为诊断越深，生成的结构越对。 |

### 1.3 核心类比

如果 Notion 是一块空地 + 工具箱，deep-custom Designer 就是请了一个**建筑师**——先看你的地块、问你的生活习惯、理解你的审美，然后给你画一套完整的建筑图纸，并帮你把房子盖起来。

## 2. 当前阶段唯一用户

### 2.1 用户画像

**深度知识工作者**——同时满足以下全部条件：

1. **有大量个人知识资产**：桌面/文件夹里有数百篇随手记录的 `.docx` / `.md` / `.txt` 文件，内容跨 3+ 个领域，跨度 6+ 个月
2. **愿意提供文件夹和文件**：不是"上传几张截图看看"，而是愿意把整个文件夹交给系统做全量分析
3. **愿意回答诊断问题**：当系统发现信息不足以判断时，用户愿意花 2-5 分钟回答追问（例如"你写交易复盘的主要目的是记录、优化策略、还是情绪宣泄？"）
4. **有强烈复盘、整理、分析、报告需求**：不只是"把文件归个类"，而是想从自己的知识积累中**看出规律、发现盲区、验证信念**
5. **愿意为定制交付付费**：认可"为我个人生成一套知识管理系统"的价值，愿意按诊断深度或交付质量付费

### 2.2 用户不愿意做的事

- 自己设计分类体系（太难、太费时间、不知道什么是好的结构）
- 手动迁移几百篇文档到新结构（纯体力活，且容易出错）
- 维护复杂的 schema 和配置（用户不是工程师）
- 从空白模板开始填内容（用户要的是"已经有了我的文件，直接能看的报告"）

### 2.3 为什么当前阶段只服务这一类用户

- deep-custom 的核心能力（深度诊断 → 个性化生成）对这类用户的**价值密度最高**。一个愿意让系统深度分析自己的用户，得到的是"过去三个月自己都没看出来的认知变化"——这种体验是 deep-custom 独有的。
- 如果先去服务"随便试试"的用户（quick-start 模式），系统会退化成一个"好看的文件分类器"，失去了差异化。
- **先做深度，再做广度。深度做好了，广度是自然延伸。反过来做，深度永远做不出来。**

## 3. 核心价值假设

以下是当前阶段所有产品决策背后的假设。每个假设都需要在真实用户反馈中验证或推翻。

### H1：用户愿意为"帮我生成适合我的知识库系统"付费

**如果为真**：deep-custom 的核心价值闭环成立——诊断越深 → 生成越准 → 用户越愿意付费 → 投入越多诊断能力。

**如果为假**：用户只想要"免费的文件分类器"，deep-custom 不成立。需要 pivot 到"极简自动分类工具"。

**当前证据**：本项目已有 32 个 CLI 命令 + MCP 服务 + Streamlit GUI，用户仍在持续使用并提出深度需求（交易系统构建、认知画像、知识盲区）。说明用户对这个方向有真实需求。

### H2：用户不想自己迁移工作流

**如果为真**：deep-custom 必须做到"用户只需要提供文件和回答，剩下全自动"。用户不需要知道 kB_tool 怎么配置、SQLite 怎么建表、FTS5 怎么索引。

**如果为假**：用户愿意手动配置，那我们的交付物可以更"工具箱化"而非"全自动生成"。

**当前证据**：项目已有的 `weekly-organize` 和 `docs-migrate` 已经验证了"自动迁移"的价值。用户从未主动修改 `config.yaml` 中的 scanner/workflow 参数——说明用户确实不想手动配置。

### H3：用户更在意第一份报告和结构是否惊艳

**如果为真**：首印效应决定一切。第一次交付不仅要"正确"，还要让用户产生"这个系统比我想的更懂我"的感觉。这要求诊断流程足够深入。

**如果为假**：用户愿意接受"v1 粗糙，v2 迭代"的节奏，那我们可以先做浅层诊断快速上线。

**当前证据**：项目 Phase 1 时用户对 UI mockup 的反馈比文字描述准确 10 倍。用户对"第一眼看到的东西"极度敏感。这个假设大概率成立。

### H4：用户不想维护复杂 schema

**如果为真**：`classification_policy.yaml`、`query_strategy_policy.yaml` 这些配置文件对用户来说必须是"系统自动生成并持续更新的黑盒"。用户只需要看报告和给反馈，不需要看配置文件。

**如果为假**：用户愿意手动调参，我们可以暴露更多配置接口。

**当前证据**：本项目 `config.yaml` 有 134 行，用户从未主动修改过非 GUI 可编辑的部分。强证据支持此假设。

### H5：用户希望系统从反馈中自动修正

**如果为真**：deep-custom 必须具备反馈闭环——用户说"这个分类不对"或"这个报告没看出什么新东西"，系统能自动调整后续的分类策略和报告模板。

**如果为假**：用户愿意接受"静态配置"，不需反馈机制。

**当前证据**：项目已有的 `review_ui.py`（人工复核 + CSV 写回）和 `tag_normalizer.py`（标签归一化）已经铺设了反馈闭环的技术基础。这些模块的存在本身就说明用户需要反馈修正能力。

## 4. 标准流程

以下流程描述一次完整的 deep-custom 交付。每个步骤的输出是下一步的输入。

```
Phase A: 诊断 — 理解用户是谁，知道什么，缺什么
┌─────────────────────────────────────────────────────┐
│ A1. 读取已有信息                                      │
│     输入：用户提供的文件夹（全量文件）+ 用户已在项目 │
│           中填写的回答（如有）                         │
│     动作：全量扫描 → 提取文本 → LLM 通读采样 →        │
│           生成初始用户画像                             │
│     输出：user_knowledge_profile.json (v0)            │
├─────────────────────────────────────────────────────┤
│ A2. 找出缺失信息                                      │
│     动作：对比画像中的"已知"和"待确认"字段，识别      │
│           信息缺口——哪些领域用户的文件覆盖了但没有      │
│           明确表述？哪些认知矛盾需要用户澄清？          │
│     输出：diagnostic_gap_list (内部，不对外)           │
├─────────────────────────────────────────────────────┤
│ A3. 动态追问                                          │
│     动作：向用户提出 5-8 个追问（按优先级排序）。问题  │
│           是动态生成的——来自对文件内容的实际分析，不是  │
│           固定问卷模板。例如：                          │
│           "你在 2025-09 到 2026-01 期间反复提到'止损   │
│            执行不力'，但 2026-02 之后这个话题消失了。   │
│            是不再困扰你了，还是不再记录了？"            │
│     输出：用户回答（追加到画像中）                      │
│     更新：user_knowledge_profile.json (v1)            │
└─────────────────────────────────────────────────────┘

Phase B: 设计 — 为用户生成专属知识库蓝图
┌─────────────────────────────────────────────────────┐
│ B1. 生成知识库蓝图                                    │
│     输入：完整用户画像 (v1) + 全量文件分析结果         │
│     动作：LLM 综合用户的知识领域、认知特点、使用习惯，  │
│           生成专属的知识库结构设计                      │
│     输出：knowledge_blueprint.md                      │
│     内容：                                            │
│     - 推荐的一级/二级分类体系（含每个分类的定义和边界） │
│     - 推荐标签策略（哪些维度打标签，标签粒度）         │
│     - 推荐的知识间关联模式（哪些分类之间存在引用关系） │
│     - 推荐的整理频率（哪些分类需要周更/月更/季更）     │
│     - 与用户当前分类体系的差异分析                     │
├─────────────────────────────────────────────────────┤
│ B2. 生成组件计划                                      │
│     动作：将蓝图拆解为可生成的具体组件                 │
│     输出：component_plan.yaml                         │
│     内容：                                            │
│     - classification_policy：分类规则 + 排除规则 +    │
│       置信度阈值                                       │
│     - query_strategy：不同问题类型的检索优先级         │
│       （关键词 vs 语义 vs 时间序列）                   │
│     - sampling_strategy：不同文档类型的采样策略        │
│     - report_templates：需要生成哪些类型的报告         │
│       （月报/季报/专题分析/认知演化/知识盲区）          │
│     - organize_schedule：自动整理的时间策略            │
│     - feedback_rules：如何将用户反馈转化为策略调整     │
├─────────────────────────────────────────────────────┤
│ B3. 生成组件                                          │
│     动作：按 component_plan.yaml 逐组件生成具体文件    │
│     输出：                                            │
│     - classification_policy.yaml                      │
│     - query_strategy_policy.yaml                      │
│     - sampling_manifest.md                            │
│     （这些文件对用户透明，由系统内部使用）              │
└─────────────────────────────────────────────────────┘

Phase C: 验证 — 在小样本上验证设计质量
┌─────────────────────────────────────────────────────┐
│ C1. 分层均匀小样本采样                                │
│     动作：从用户全量文件中按 (分类 × 时间段) 分层     │
│           均匀采样，取 10-20% 的文件作为样本集          │
│     输出：sample_knowledge_map.md                     │
│     内容：样本集的文件清单 + 分层分布 + 覆盖度检查     │
├─────────────────────────────────────────────────────┤
│ C2. Sample-Run                                        │
│     动作：用新的分类策略处理样本集 → 生成样本报告      │
│     检查：                                            │
│     - 每个分类是否有足够样本？（太少=分类太细）        │
│     - 是否有文件被分到"无法判断"？（太多=分类有盲区）  │
│     - 分类置信度分布是否合理？                         │
│     - 报告是否能从样本中提取出有意义的洞察？           │
├─────────────────────────────────────────────────────┤
│ C3. 用户反馈                                          │
│     动作：将 sample-run 的结果（分类结果 + 报告预览）  │
│           呈现给用户，收集反馈                          │
│     典型反馈形式：                                     │
│     - "这个分类我不需要，和那个合并吧"                 │
│     - "这个文件不应该被排除"                           │
│     - "这个报告发现了我想过但没写下来的东西"           │
│     输出：原始反馈文本                                 │
├─────────────────────────────────────────────────────┤
│ C4. 反馈转规则                                        │
│     动作：LLM 将用户反馈转化为可执行的规则更新          │
│     输出：feedback_rules.yaml                         │
│     内容：每条反馈 → 对应的分类策略/标签策略/报告       │
│           模板的修改指令                                │
│     更新：classification_policy.yaml、                │
│           query_strategy_policy.yaml、                │
│           sampling_manifest.md                        │
├─────────────────────────────────────────────────────┤
│ C5. 重新 Sample-Run（如需要）                          │
│     条件：C4 的规则修改较大（影响 >20% 的文件分类或    │
│           报告结构有重大变化）                          │
│     动作：用更新后的策略重新处理样本集 → 再次呈现给用户 │
│     循环 C3 → C4 → C5，直到用户确认或放弃              │
│     防护：最多 3 轮 sample-run，超过则标记为需要手动    │
│           介入的边缘 case                              │
└─────────────────────────────────────────────────────┘

Phase D: 构建 — 正式生成完整 deep-custom 知识库
┌─────────────────────────────────────────────────────┐
│ D1. 全量构建                                          │
│     动作：用最终通过的策略处理全量文件                  │
│     输出：final_config.yaml（用户知识库的最终配置）    │
│     动作：执行全量分类入库 → 生成所有报告               │
├─────────────────────────────────────────────────────┤
│ D2. 输出第一份高质量报告                               │
│     输出：first_value_report.md                       │
│     内容：                                            │
│     - 知识库全景概览（分类分布/时间分布/内容量）       │
│     - 认知画像（长期关注主题/决策模式/情绪模式）       │
│     - 知识演化发现（跨时间的认知变化/被证伪的旧信念）  │
│     - 知识盲区提示（应该关注但未涉及的话题）            │
│     - 使用建议（哪些报告适合什么时候看/怎么用）         │
│     - "你过去没看到的东西"（deep-custom 的核心价值）    │
│     要求：这份报告必须让用户产生"这个系统比我想的更     │
│           懂我"的感觉。这是 deep-custom 的第一印象。    │
└─────────────────────────────────────────────────────┘

Phase E: 持续演化（后续迭代）
┌─────────────────────────────────────────────────────┐
│ E1. 用户继续给反馈 → 系统自动调整策略                  │
│ E2. 用户新增文件 → 系统自动整理 + 更新画像              │
│ E3. 定期重新诊断 → 用户的知识结构变化 → 建议结构调整   │
│ E4. 新报告类型 → 根据用户的使用模式推荐                 │
└─────────────────────────────────────────────────────┘
```

## 5. 核心交付物

### 5.1 交付物清单与规范

| 交付物 | 类型 | 面向谁 | 内容说明 |
|--------|------|--------|---------|
| `user_knowledge_profile.json` | 结构化数据 | 系统内部 | 用户知识画像：关注领域/认知特点/决策模式/术语表/开放问题清单。由 Phase A 生成，后续持续更新。 |
| `knowledge_blueprint.md` | 文档 | 用户可见 | 知识库蓝图：推荐分类体系 + 标签策略 + 关联模式 + 整理节奏。用户的核心决策文档。 |
| `component_plan.yaml` | 配置 | 系统内部 | 组件计划：classification_policy / query_strategy / sampling_strategy / report_templates / organize_schedule / feedback_rules 的生成计划。 |
| `classification_policy.yaml` | 配置 | 系统内部 | 分类策略：primary_category 列表 + 每类的 scope 定义 + 边界 case 处理规则 + 排除规则 + 置信度阈值 + 规则/LM 混合策略配置。 |
| `query_strategy_policy.yaml` | 配置 | 系统内部 | 检索策略：不同 query 类型的检索方法优先级（keyword FTS → chunk search → agentic multi-turn），每种方法的权重和 fallback 链。 |
| `sampling_manifest.md` | 文档 | 系统内部 | 采样策略：不同文档类型/长度的采样方法，deep read 触发条件，关键词上下文窗口配置。 |
| `sample_knowledge_map.md` | 文档 | 用户可见 | 样本知识地图：分层采样结果 + 分类覆盖度检查 + 样本报告预览。用户反馈的直接对象。 |
| `feedback_rules.yaml` | 配置 | 系统内部 | 反馈规则：用户反馈 → 策略修改的映射。每条规则包含：触发条件 + 修改目标 + 修改动作 + 影响范围。 |
| `final_config.yaml` | 配置 | 系统内部 | 最终配置：综合了蓝图 + 组件 + 反馈后的完整运行配置。可直接被 kB_tool 加载运行。 |
| `first_value_report.md` | 文档 | 用户可见 | 第一份深度报告：全景概览 + 认知画像 + 演化发现 + 盲区提示 + 使用建议。这是 deep-custom 价值的最终证明。 |

### 5.2 交付物关系

```
user_knowledge_profile.json ──→ knowledge_blueprint.md ──→ component_plan.yaml
                                                                  │
                                    ┌─────────────────────────────┤
                                    ▼                             ▼
                         classification_policy.yaml    query_strategy_policy.yaml
                         sampling_manifest.md
                                    │
                                    ▼
                         sample_knowledge_map.md ──→ 用户反馈
                                                            │
                                                            ▼
                                                  feedback_rules.yaml
                                                            │
                                                            ▼
                                                    final_config.yaml
                                                            │
                                                            ▼
                                                  first_value_report.md
```

### 5.3 各交付物的质量标准

**user_knowledge_profile.json**：
- 至少识别 3 个主要知识领域
- 每个领域至少 2 个可验证的特征描述
- 术语表至少 10 个高频概念
- 至少 3 个开放问题（用户自己可能没意识到的问题）

**knowledge_blueprint.md**：
- 分类体系有明确的边界定义（不是"AI相关"这种模糊描述）
- 每个分类有入/出标准（什么文件应该/不应该进这个分类）
- 分类总数控制在 5-15 之间（太少无用，太多难维护）
- 有"与用户当前结构的差异"说明

**first_value_report.md**：
- 至少包含 3 个用户"过去没看到"的发现
- 每条发现附证据（具体文件引用）
- 盲区提示是具体可操作的（不是"你应该多关注 XX"，而是"你在 XX 话题上只有 2 篇文档，而同类用户通常有 15+ 篇"）
- 阅读体验应该是"报告"而非"日志"——有叙事、有洞察、有建议

## 6. 成功标准

以下标准用于判断 deep-custom 是否达到"可交付"水平。全部满足 = 成功。

### S1：用户认为结构明显比自己整理强

**判断方式**：用户看完 `knowledge_blueprint.md` 后，不需要自己动手改分类。如果用户在看完蓝图后说"这个分类比我原来的好，就这么用"，S1 达标。如果用户开始手动调整分类名称/边界，S1 未达标。

**为什么重要**：如果用户还是要自己设计分类，那 deep-custom 没有创造价值——只是换了个界面让用户做和以前一样的事。

### S2：用户能通过报告看到过去没有看出的东西

**判断方式**：`first_value_report.md` 中至少有 3 个发现让用户产生"确实，我从来没这么想过"的反应。如果报告只是把用户的文件汇总了一遍但没有新洞察，S2 未达标。

**为什么重要**：这是 deep-custom 和"文件分类器"的本质区别。分类准确是及格线，发现用户自己不知道的东西才是 deep。

### S3：用户愿意继续给反馈

**判断方式**：用户在收到第一份报告后，主动给出了至少一次反馈（不是被追问的，是主动的）。或者用户在 Phase C 的反馈环节给出了超过一句话的详细反馈。如果用户说"行了就这样吧"然后不再互动，S3 未达标。

**为什么重要**：deep-custom 需要反馈闭环才能持续演化。如果用户懒得给反馈，系统就会停滞在初始版本。

### S4：用户愿意把更多文件交给系统

**判断方式**：用户在第一次交付后，主动把新的文件夹/新的文件源加入系统。如果用户只用了最初提供的文件就停了，S4 未达标。

**为什么重要**：这意味着用户认为 deep-custom 有持续价值，不只是"一次性项目"。从"试用"变成"日常使用"的关键信号。

### S5：用户愿意为定制交付付费

**判断方式**：用户在看到 `first_value_report.md` 后，表达了付费意愿（"这个值得付钱""如果持续做下去我会付费"等）。如果用户说"挺好的但不会掏钱"，S5 未达标。

**为什么重要**：这是商业可行性的最终验证。免费的东西用户说"好"，付费的东西用户说"值"。我们要的是"值"。

## 7. 失败标准

以下标准用于判断 deep-custom 是否偏离了方向。任一发生 = 需要 pivot。

### F1：只是分类准确但不惊艳

**现象**：用户说"分得挺对的"但没有后续动作。Dashboard 数据看起来干净，但用户没有惊喜感。

**根因**：系统退化成了"更好的文件分类器"而非"知识库设计师"。分类是手段，洞察是目的。如果只做好了手段而丢掉了目的，deep 丢了。

**应对**：回溯到 Phase A——诊断深度不够。是不是追问太少？是不是画像维度太浅？是不是只看了文件内容而没有理解文件之间的关系？

### F2：用户看完 dashboard 后不知道下一步干什么

**现象**：用户打开报告/蓝图，扫了一遍，然后关掉了。没有"所以我现在应该……"的行动冲动。

**根因**：交付物是"信息"而非"建议"。`first_value_report.md` 必须回答"所以呢？"——不仅是"你过去写了什么"，更是"你接下来应该关注什么"。

**应对**：检查报告的"使用建议"部分是否足够具体。不是在报告末尾加一个委婉的"建议继续记录"，而是给出可操作的具体指令："下周开始，在你写每篇交易复盘时，额外记录一个字段：本次决策时最依赖的规则是哪条。我们会追踪你的规则依赖度随时间的变化。"

### F3：用户不愿继续回答问题

**现象**：Phase A 的追问发出后，用户 24 小时内没有回复。或者回答极短（"是""不是""差不多"）。

**根因**：追问太浅（用户觉得不用回答）或太烦（用户觉得太累）。追问必须满足两个条件：① 用户觉得这个问题有意思，愿意想 ② 回答这个问题不需要太费力。用文件中的具体引用来构造追问（"你在 XX 文档里说 YY，但 ZZ 文档里说 WW——这两个矛盾吗？"），比泛泛的"你主要关注哪些领域？"效果好 10 倍。

**应对**：减少追问数量（5-8 → 3-5），提高追问质量（每一条必须引用用户的具体文件内容）。

### F4：用户觉得和普通文件搜索差不多

**现象**：用户说"这不就是搜一下再总结一下吗？AI 也能做啊。"

**根因**：deep-custom 的差异化没有体现——用户看不到"个性化生成"和"通用 LLM 总结"的区别。

**应对**：检查交付物中是否有"只属于这个用户"的内容——用户独有的概念术语、用户特有的认知矛盾、用户个人历史中的关键转折。这些是通用 LLM 做不出来的，因为它们需要长期记忆和跨文档关联。

### F5：用户没有持续复用场景

**现象**：第一次交付后，用户没有再次使用系统（没有新增文件、没有看后续报告、没有再次搜索）。

**根因**：deep-custom 是一次性的"咨询项目"而非"持续运行的系统"。系统必须有"日常模式"——每周有新文件进来，每月有新报告出来，每季有认知演化追踪。如果第一次交付就是终点，系统就没有长期价值。

**应对**：Phase D 之后必须有自动持续运行的能力——每周整理、每月报告、每季演化追踪。这些在现有 kB_tool 中已基本实现（weekly-organize / monthly-report / quarterly-report），关键是 deep-custom 生成的是为这个用户量身定制的版本。

## 8. 明确的边界：本阶段不做

以下每一项都是经过有意取舍的。不做不是因为做不到，而是因为这些会稀释 deep-custom 的核心价值。

| 不做 | 原因 | 什么时候可能做 |
|------|------|---------------|
| quick-start 模式 | 5 分钟上手的体验和 2 小时深度诊断的体验是矛盾的。做 quick-start = 降低诊断深度 = 生成质量下降 | deep-custom 的核心流程稳定后，可以从中提取一个"轻量预览"模式 |
| guided-custom 模式 | "引导式定制"介于 quick-start 和 deep-custom 之间，是不上不下的中间态。要么全自动要么深度定制 | 评估 deep-custom 和 quick-start 之间的真实用户需求后再决定 |
| 浅层问卷 | 问卷只能问"你喜欢什么颜色""你关注哪些领域"——这些 LLM 读文件就能推断出来。不需要问 | 永远不做。诊断永远基于文件内容分析 + 动态追问，不基于固定问卷 |
| 多用户平台 | 引入权限、隔离、协作 → 工程复杂度翻 3 倍 → 深度诊断能力被分散 | deep-custom 在一个用户上验证成功后 |
| 模板市场 | 模板是通用化的，deep-custom 是个性化的。做模板市场 = 承认"个性化生成不够好，用户还是得选模板" | 如果验证发现部分用户确实不需要深度定制，那时才考虑 |
| 通用插件平台 | 插件生态的前提是有足够多的用户和开发者。当前只有一个深度用户 | deep-custom 有 100+ 用户后 |
| 完整 MCP 商业化 | MCP 是对外协议，不是产品。商业化 MCP 服务是另一个产品方向 | deep-custom 核心价值被验证后，作为分发渠道之一 |
| 大而全知识库软件 | "做一个更好的 Notion"是错的方向。我们做的是"给你一个只属于你的 Notion" | 永远不做。这不是我们的赛道 |
