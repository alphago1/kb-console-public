# Product Direction: Tag-first 个性化知识库 v4

> 冻结方向：2026-05-05
> 产品类型：Tag-first 个性化知识库
> 核心差异化：通过深度问答生成用户专属 Tag 体系，多维标注本地文件，实现精准召回

---

## 1. 为什么不是 Wiki-first

Wiki-first 模式假设用户愿意维护一个结构化的知识 wiki，作为系统的"单一事实源"。这个假设在当前场景下不成立：

### 1.1 维护成本过高
- Wiki 需要用户持续手动创建、更新、整理页面。对于个人知识库用户，这是不可持续的负担。
- 用户的文件以 Word/docx/md/txt 形式自然产生，写作行为已经完成了一次"知识编码"——要求用户再做一次 wiki 化编码，是重复劳动。

### 1.2 Wiki 不适合作为检索锚点
- Wiki 页面是对原始文件的二次摘要，天然存在信息损失。
- 当用户搜索"2026年3月关于止损的反思"时，应该直接命中包含该内容的原始文件，而不是先经过 wiki 页面的中间层。
- Wiki 页面之间的链接关系需要人工维护，链路断裂后检索质量会退化。

### 1.3 Wiki 不适合作为 AI 的事实源
- AI 需要的是原始证据（evidence），不是人工整理后的叙述。
- Wiki 页面无法追溯"这个结论是从哪份文件的哪段话来的"，缺乏可验证性。

### 结论
Wiki 不是主线，不是事实源，不是用户必须维护的系统。Wiki 是由 tags 和 evidence 生成的主题摘要缓存层。

## 2. 为什么不是 Embedding-first

Embedding-first（向量检索优先）是当前 AI 知识库的主流方案，但在这个场景下不是最优解：

### 2.1 语义近似 ≠ 精确匹配
- Embedding 检索返回"语义相似"的内容，但用户查询"2026年3月的交易复盘"时，需要的是精确的 category + time 过滤，不是语义近似。
- 在个人知识库场景中，结构化元数据（category、tags、time、source_type）的区分力远高于向量相似度。

### 2.2 Embedding 不可解释
- 用户无法理解"为什么这篇文档被召回"——Embedding 是黑盒。
- Tag-first 方案中，每篇文档的 tags 是透明的，用户可以检查、修正、补充，形成反馈闭环。

### 2.3 Embedding 成本与规模不匹配
- 个人知识库文档量在数百到数千级别，不需要近似检索来处理规模问题。
- 精确的结构化过滤（tags + time + category）在这个规模下既快又准。

### 2.4 但 Embedding 不是被排除的
- Embedding 作为辅助召回通道存在（处理"这个概念用不同说法表达"的场景）。
- 但召回的主路径永远是 category → tags → time → source_type，Embedding 仅作为补充。

## 3. 为什么是 Tag-first

### 3.1 Tag 是用户认知的自然表达
- 用户在回答深度问题时，自然流露出他们对知识领域的划分方式。例如：
  - "我把交易分为：入场策略、止损管理、仓位管理、心理纪律、复盘总结"
  - 这 5 个词就是用户的 tag ontology 雏形。
- Tag-first 的核心洞察：**分类体系和 tag 体系应该从用户自己的语言中生长出来，而不是从通用模板中套用。**

### 3.2 Tag 是多维的
- 一个文档可以同时被打上多个维度的 tag：
  - **领域维度**：`交易/止损` `AI/RAG` `个人成长`
  - **时间维度**：`2026-03` `Q1`
  - **文档类型维度**：`复盘` `学习笔记` `项目想法` `草稿`
  - **情绪/状态维度**：`反思` `兴奋` `困惑` `阶段性总结`
  - **关联维度**：`与XX项目相关` `前置知识` `后续跟进`
- 多维 tag 使得同一篇文档可以从不同入口被召回。

### 3.3 Tag 支持精准召回
- 用户查询"我关于止损的反思，最近三个月"时，系统执行：
  1. tag 过滤：`tags CONTAINS '止损' AND tags CONTAINS '反思'`
  2. time 过滤：`created_at >= '2026-02-05'`
  3. category 过滤：`category = '交易复盘'`
  4. 排序：按时间倒序
- 每一步都是确定性的，可解释的，可调试的。

### 3.4 Tag 体系可以进化
- 用户的新回答、新文件、新搜索行为都可以触发 tag 体系的更新。
- 例如用户新增了一个领域"量化交易"，系统可以通过问答确认是否需要在 tag ontology 中新增相关 tags。

## 4. Category 和 Tags 的关系

### 4.1 Category 是粗粒度的空间划分
- Category 回答"这个文件属于哪个文件夹/领域"。
- 每个文件只有一个 category（互斥），例如：
  - `交易复盘`
  - `交易系统与方法论`
  - `AI与工具化`
  - `个人随笔与自我观察`
  - `项目想法与反复出现的问题`

### 4.2 Tags 是细粒度的多维标注
- Tags 回答"这个文件涉及哪些主题、概念、状态"。
- 每个文件可以有多个 tags（非互斥），例如：
  - `止损` `执行力` `心理纪律` `2026-03` `反思` `阶段性总结`

### 4.3 关系总结
```
Category:  文件属于哪个"房间"     → 1:1，互斥
Tags:      文件涉及哪些"标签"     → 1:N，多维
Time:      文件的时间锚点          → 天然属性
Source:    文件的格式来源          → 天然属性

召回路径：Category（定位房间）→ Tags（定位标签）→ Time（时间窗口）→ Source（格式过滤）
```

### 4.4 Tag Ontology 的结构
Tag 不是扁平的 keyword 列表，而是有层次的本体：

```
交易（domain）
├── 入场策略（concept）
│   ├── 突破入场（method）
│   └── 回调入场（method）
├── 止损管理（concept）
│   ├── 固定止损（method）
│   ├── 移动止损（method）
│   └── 时间止损（method）
├── 仓位管理（concept）
├── 心理纪律（concept）
└── 复盘总结（activity）

AI与工具化（domain）
├── RAG（concept）
├── Agent（concept）
├── Embedding（concept）
└── 本地部署（method）

个人成长（domain）
├── 反思（state）
├── 年度目标（activity）
└── 习惯追踪（activity）
```

这个 ontology 由用户的深度问答决定，不是预设的。

## 5. 用户回答如何决定 Tag Ontology

### 5.1 深度问答流程

```
Phase 1: 领域发现
  Q: "你平时写哪些类型的文档？按重要性排序。"
  A: "交易复盘最重要，其次是 AI 学习笔记，偶尔写个人反思。"
  → 生成 domain 级 tags: 交易, AI与工具化, 个人成长

Phase 2: 概念挖掘
  Q: "在交易方面，你最常思考哪些具体问题？"
  A: "主要是止损执行不到位，还有仓位忽大忽小，入场时机把握也不好。"
  → 生成 concept 级 tags: 止损, 仓位管理, 入场策略

Phase 3: 关系建立
  Q: "止损和仓位管理之间有联系吗？还是一起出现的？"
  A: "经常一起出现，我仓位大的时候止损就犹豫。"
  → 建立 tag 关联: 仓位管理 ↔ 心理纪律 ↔ 止损

Phase 4: 时间偏好
  Q: "你回顾交易时，是按月份看还是按季度看？"
  A: "按月看，每个月做一次总结。"
  → 时间粒度: monthly, tag 自动带上月份

Phase 5: 输出偏好
  Q: "你希望系统给你生成什么类型的输出？"
  A: "月报最重要，然后是按主题的深度分析。"
  → 输出组件: monthly_report, topic_deep_dive
```

### 5.2 从回答到 Tag 体系的映射规则

| 用户回答中的信号 | 映射为 |
|---|---|
| "我主要写 X、Y、Z" | domain 级 category |
| "经常遇到 A 问题" | concept 级 tag |
| "A 和 B 有关联" | tag 关联边 |
| "按月/周/季度" | 时间粒度 |
| "重要的/不太重要的" | tag 权重 |
| "最近在关注 X" | 临时高优先级 tag |
| "这个已经不再做了" | 归档/降权 tag |

### 5.3 Tag 体系的持续进化
- 新文件入库时，LLM 根据已有 tag ontology 进行标注
- 用户可以通过搜索行为隐式反馈（搜不到 → 缺 tag）
- 系统定期检查 tag 使用频率，低频 tag 建议合并或删除
- 用户新增领域的文件时，触发补充问答

## 6. Wiki 在系统中的正确位置

### 6.1 Wiki 的重新定位
```
旧定位（错误）: Wiki 是知识库的核心，用户维护 wiki 页面，文件是附件
新定位（正确）: Wiki 是由 tags + evidence 自动生成的主题摘要缓存层
```

### 6.2 Wiki 的角色
1. **AI 快速读取层**：当 AI 需要了解"用户关于止损的整体认知"时，先读 wiki 缓存而不是遍历所有文件
2. **人类可浏览层**：用户可以浏览自动生成的 wiki 页面，但不强制维护
3. **路由层**：查询时先匹配 wiki 页面标题，命中后直接返回对应页面的摘要 + 源文件引用

### 6.3 Wiki 的生成机制
```
触发条件：某个 tag 下的文档 ≥ N 篇（默认 N=3），或用户手动触发
生成过程：
  1. 聚合该 tag 下的所有文档作为 evidence
  2. LLM 生成主题摘要（300-800 字）
  3. 提取关键观点、时间线、矛盾点
  4. 列出源文件引用（可点击跳转）
  5. 写入 wiki 缓存层
过期策略：当该 tag 下新增文档时，标记 wiki 页面为 stale，下次访问时重新生成
```

### 6.4 Wiki 不是
- ❌ 不是用户必须手动编辑的页面
- ❌ 不是系统的事实源
- ❌ 不是检索的第一入口
- ❌ 不需要维护内部链接网络

### 6.5 Wiki 是
- ✅ 高频 tag 主题的自动摘要缓存
- ✅ AI 的快速上下文加载层
- ✅ 人类可选的浏览入口
- ✅ 可由 tags + evidence 随时重建

## 7. 主线功能 vs Experimental 功能边界

### 7.1 主线功能（Tag-first，稳定 API，长期维护）

| 功能 | 说明 | 状态 |
|---|---|---|
| 深度问答 → Tag Ontology 生成 | 通过多轮问答生成用户专属分类+tag体系 | 主线 |
| 文件多维 Tag 标注 | LLM 根据 tag ontology 对新文件自动标注 | 主线 |
| Tag-first 检索 | category → tags → time → source_type 四级召回 | 主线 |
| Tag 体系进化 | 根据新文件/搜索行为更新 tag 体系 | 主线 |
| 月度/季度报告 | 基于 tag 聚合生成报告 | 主线 |
| Wiki 缓存层 | 由 tags + evidence 自动生成，AI 快速读取 | 主线 |
| 文件扫描与入库 | 支持 docx/md/txt，自动提取文本 | 主线 |
| FTS 全文搜索 | SQLite FTS5 作为兜底检索 | 主线 |
| Dashboard | 文件统计、tag 分布、写作趋势 | 主线 |

### 7.2 Experimental 功能（可能变更或移除）

| 功能 | 说明 | 状态 |
|---|---|---|
| MCP Server | 对外暴露工具的协议服务 | Experimental |
| Agent 工具调用 | 多轮 agent 自主调用工具 | Experimental |
| Embedding 检索 | 向量相似度作为辅助召回 | Experimental |
| Streamlit GUI Wiki Reading 页 | 人类浏览 wiki 的 UI | Experimental |
| 手动 Wiki 编辑 | 用户直接编辑 wiki 页面 | 已废弃 |
| Karpathy Baseline 完整适配 | 基线系统的全部组件 | Experimental |

### 7.3 边界原则
- 主线功能必须在 `test-all` 中覆盖
- Experimental 功能可以没有测试覆盖
- 主线功能的接口变更需要更新测试
- Experimental 功能可以随时降级或移除，不影响主线

## 9. 与旧版的区别

| 维度 | 旧版（Wiki-first / mixed） | 新版（Tag-first v4） |
|---|---|---|
| 核心抽象 | Wiki 页面 | Tag Ontology |
| 用户负担 | 需要维护 wiki | 只需回答深度问题 |
| 检索路径 | Wiki 路由 → FTS | Category → Tags → Time → Source |
| Wiki 角色 | 知识库核心 | 自动生成的缓存层 |
| 个性化来源 | 通用模板 + 手动调整 | 深度问答 → 专属 ontology |
| 文件标注 | 单一分类 | 多维 tags |
| 可解释性 | 中等 | 高（每条召回都有 tag 依据） |
| 可进化性 | 低（wiki 结构固化） | 高（tag 体系随用户进化） |
