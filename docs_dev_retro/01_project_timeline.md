# 01 — 项目成长时间线

**用途**：记录项目方向如何一步步演化，重点不在流水账而在"为什么转向"。

**读者**：自己（理解项目演进规律）/ 做类似项目的人。

---

## Phase 0：CLI 原型期

**时间**：2025-04 ~ 2026-05-02

**当时目标**：把桌面 Word 文件自动分类、存储、检索。先用 CLI 把核心链路跑通。

**主要实现**：
- `kb_tool/` 后端：32 个 CLI 命令（scan/export/search/weekly-organize/token-budget 等）
- SQLite + FTS5 全文检索
- DeepSeek LLM 自动分类
- MCP Server（Stdio + HTTP）+ Agent Runtime（7 个工具）
- Streamlit GUI v1：391 行，9 个平铺页面

**为什么进入下一阶段**：
CLI 功能完整但 GUI 体验粗糙。用户实际使用时发现多个阻塞性 bug（DB 不存在、中文乱码），且 UI 设计明显不适合日常使用。

**当时的误判或风险**：
- `fingerprint_sha256` 基于随机采样文本计算——这是整个项目最大的设计隐患，但 Phase 0 时完全没意识到
- config.yaml 中路径全部是相对路径——在 CLI 单一工作目录下没问题，但换了工作目录就崩
- 以为 9 个平铺页面够用了，没有考虑导航层次

**这个阶段留下了哪些有效资产**：
- 32 个 CLI 命令的完整后端——后续 GUI 重构只改前端，后端几乎没动
- MCP + Agent 基础设施——后来智能搜索直接复用
- SQLite 数据库 schema——稳定，只在加列没改结构
- `docs/` 知识库目录结构（11 个分类 × 12 个月）

**现在回头看，这一阶段的经验**：
> 原型阶段的 hack（随机采样做 SHA、相对路径）如果不及时修正，会变成系统级 bug。原型可以糙，但"数据指纹"和"路径解析"这两件事必须从一开始就做对。

## Phase 1：Bug 发现 + 需求明确 + UI 原型

**时间**：2026-05-03 上午 ~ 下午

**当时目标**：修掉已知 bug，理解用户真正想要的 GUI 是什么样。

**主要实现**：
- BUG-001~004 修复（DB 初始化、中文编码、agent_test 统计、缺失文件报错）
- 写了 170+ 条的测试用例文档
- 用户逐页给出详细反馈：
  - "所有的按键有中文解释的写中文解释 英文作为括号内容"
  - "交易分析不太好这么安排 最好将其作为个性功能的一个子栏目"
  - "profile-me scope 让用户自己填"
  - "查找不能是朴素的关键词 要的是大模型搜索"
  - "设置为什么是只读？改成可读可写"
- 创建 `ui-mockup/` 纯前端模拟网站，用户看了效果后确认方向

**为什么进入下一阶段**：
用户反馈清晰了，UI 原型验证了，可以动手重写 GUI。

**当时的误判或风险**：
- 第一次写 v2 plan 时保留了"交易分析"这个硬编码名称——用户纠正后才改成"自定义分析"
- 最初计划用 Embedding 做智能搜索——用户说"无论是查wiki还是embedding还是agentic search都好"，选择了更简单的 Agentic 方案

**这个阶段留下了哪些有效资产**：
- `测试用例文档.md`（170+ 用例，后来实际测试的参考）
- `ui-mockup/mock_app.py`（UI 原型，确认了设计方向）
- `plan-iterative-reddy.md`（v2 计划文档，后来基本按此执行）

**现在回头看，这一阶段的经验**：
> 在写代码之前先做 UI mockup 是最划算的时间投资。用户看了假数据原型后给的反馈比看文字描述准确 10 倍。"交易分析→自定义分析"这个关键转向，如果没有 mockup 对话可能永远不会发生。

## Phase 2：GUI v2 重写

**时间**：2026-05-03 傍晚 ~ 夜间

**当时目标**：按 v2 plan 完全重写 GUI，把后端能力用新的信息架构呈现。

**主要实现**：
- `streamlit_app.py` 完全重写（391 → ~750 行）：6 组导航 + 子页面
- `ui_helpers.py` 大幅扩展（190 → ~580 行）：
  - `run_cli_live_async()` 异步任务执行器
  - `render_task_progress()` 进度渲染
  - `save_config()` 配置读写（带备份）
  - `test_deepseek_connection()` API 连通测试
  - `get_dashboard_enriched()` 增强版 Dashboard
  - `system_health_check()` 系统诊断
  - `estimate_scope_tokens()` Token 预估
- `.streamlit/config.toml` 主题配置
- 三个批处理文件加 `chcp 65001` + `PYTHONIOENCODING=utf-8`

**为什么进入下一阶段**：
v2 上线后，用户开始实际使用。一用就发现了更多 bug（智能搜索 AttributeError、搜索无结果等）。

**当时的误判或风险**：
- 以为 `run_cli_live_async` 的 task_id 自动跨 rerun 持久化——Streamlit 每次重跑脚本，局部变量全重置
- 测试全从 `kb_tool/` 目录跑，没发现 cfg 相对路径的隐患
- 智能搜索直接调 Agent CLI——没意识到一次搜索 = 20 次 LLM API 调用的巨大延迟

**这个阶段留下了哪些有效资产**：
- 完整的新 GUI 架构（导航、异步任务、配置管理）
- 侧边栏后台任务面板

**现在回头看，这一阶段的经验**：
> 重写后的第一次上线不是终点，是新一轮 bug 发现的起点。v2 上线后 2 小时内就发现了 BUG-005~007。这个阶段留下的最大教训：**测试环境必须和运行环境完全一致**，否则测出来的"通过"是假阳性。

## Phase 3：Bug 修复马拉松

**时间**：2026-05-03 深夜 ~ 2026-05-04 凌晨

**当时目标**：修掉用户在实际使用中遇到的每一个 bug。

**主要实现**：

### 第一波：前端交互 bug（BUG-005~007）
- `st.script_run_ctx` 不存在、缺 `import json`、task_id 不持久化
- 修复后 GUI 基本可用

### 第二波：文件重复危机（BUG-008a/b/c）
用户发现 docs/ 里有大量重复文件。深入排查后发现三道防线全崩：
1. mtime 浮点精度 → 去重失败 → 同一文件被重复处理
2. `_unique_path` 机械加 `_2` 后缀 → 产生物理重复
3. **SHA 来自随机采样文本**（非确定性）→ 文件名中的指纹每次都不同 → 去重彻底失效
- 5 轮清理共删除 199 个重复文件，DB 从 400 → 153
- 修复 `fingerprint_sha256 = sha256(sampled)` → `sha256(full_text)`

### 第三波：路径 / 工作目录问题（BUG-009, 011, 012）
- **BUG-009（最严重的 bug）**：cfg 相对路径导致 GUI 读空库 → 搜索永远 0 结果。我在 `kb_tool/` 下跑测试全通过，完全没发现。用户反复说"搜索不到内容"我才意识到
- BUG-011：子进程 stdout 缓冲 → GUI 假死。`python -u` + `PYTHONUNBUFFERED=1` 修复
- BUG-012：文件夹分析路径基准用错了 root

### 第四波：LLM 调用质量问题（BUG-010, 014, 015）
- 主题分析只搜交易分类 + 0 篇文档时 LLM 编造报告
- 主题分析用 LIKE 搜文件名而非全文
- 80 篇硬上限 → 100 万字 Token 预算制 + 并发压缩合成

### 第五波：后台任务体验（BUG-013）
- 切页面后结果丢失 → render_task_progress 增强结果展示 + 侧边栏持久面板 + toast+beep 通知

**为什么进入下一阶段**：
bug 收敛了，用户开始提体验优化需求（预算制、并发、文件夹选择器）。

**当时的误判或风险**：
- 多次声称"修复完成"但实际没有从用户的角度验证——用户要的不是"代码没报错"，是"搜索能出结果"
- `PYTHONUNBUFFERED=1` 修了子进程缓冲，但没有检查其他 subprocess 调用点是否也需要——后来发现 `run_cli_collect` 也是同样问题

**这个阶段留下了哪些有效资产**：
- 199 个重复文件的清理 → 知识库从 400 到 153 真实文档
- 确定性 SHA 指纹 → 以后不会再产生重复
- 所有路径绝对化 → 工作目录不再影响行为
- 测试脚本 `tests/test_gui_backend.py`（38/39 通过）+ `tests/test_cli_commands.py`（33/33 通过）

**现在回头看，这一阶段的经验**：
> **修 bug 最浪费时间的方式是在错误的方向上排查。** BUG-009 我查了 find_idea 代码、FTS5 表结构、chunk 数据——全是正常的。如果我一开始就问自己"GUI 和 CLI 用的真的是同一个数据库吗"，5 秒就能定位。**先排除环境差异，再查代码逻辑。**

## Phase 4：体验打磨 + 文档沉淀

**时间**：2026-05-04

**当时目标**：把"能用"变成"好用"，写测试和文档防止回退。

**主要实现**：
- 文件夹选择器（浏览对话框 + 手动输入 + 快速添加）
- 后台任务侧边栏持久面板 + 完成通知
- 100 万字预算制取代硬上限
- 分批并发压缩取代串行
- 测试套件 + README + 开发Debug报告 + 复盘文档骨架

**为什么进入下一阶段**：
核心功能稳定，bug 收敛。用户开始提"下次项目怎么避免这些问题"——进入了复盘沉淀阶段。

**当时的误判或风险**：
- `compress_and_synthesize` 第一次实现时是串行的——用户指出后才改成并发
- 复盘文档结构设计偏大（10+ 文件），可能部分文件不会填满

**这个阶段留下了哪些有效资产**：
- `README.md` — 项目功能 + novelty + 后续方向
- `开发与Debug报告.md` — 全项目书写与调试记录
- `docs_dev_retro/` — 本次复盘的完整文档骨架
- `tests/` — 可重复运行的测试套件

## 关键决策时间线

| 时间 | 决策 | 如果没做会怎样 |
|------|------|------|
| Phase 1 | 先做 UI mockup 再写代码 | 可能在错误的设计方向上浪费一整天 |
| Phase 1 | 交易分析 → 自定义分析 | 系统会是一个"交易专用工具"而非"通用知识库" |
| Phase 2 | 用 Agentic Search 而非 Embedding | 需要引入向量数据库，工期翻倍 |
| Phase 3 | SHA 改为全文本 | 继续产生重复文件，知识库质量持续恶化 |
| Phase 3 | cfg 路径绝对化 | GUI 永远搜不到任何东西 |
| Phase 4 | 100 万字预算制 | LLM 上下文溢出，分析报告质量差 |
| Phase 4 | 分批并发 | 大知识库的分析要等几分钟 |
