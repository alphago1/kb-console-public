# 07 — 可复用的 Prompt 模板

**用途**：本次开发中验证过有效的 prompt 模板，下次可以直接复用或调参。

**读者**：自己（下次用 AI 时参考）/ 任何想提高 prompt 质量的人。

**怎么填**：每个 prompt 包含：场景、完整 prompt 文本、为什么有效、注意事项。

---

## 1. 项目全貌调研 prompt

**场景**：接手一个新项目或让 AI 理解项目结构

```
检查理解一下现在这个项目的情况，将情况写入到 md 文件里面
```

**为什么有效**：给 AI 充分的探索空间，不限制输出的格式和深度。

**注意事项**：在 prompt 之前应该让 AI 有足够的上下文（已读过关键文件）。

## 2. 全功能测试用例编写

**场景**：给已有系统写测试用例

```
你需要作为一名测试工程师，研究前后端的页面，
将对接的接口的所有功能都写测试用例出来，
检查每个功能是否可用是否工作正常等
```

**为什么有效**：明确了角色（测试工程师），明确了范围（前后端+接口），明确了交付物（测试用例）。

## 3. Bug 定位 prompt

**场景**：发现 bug 后让 AI 深入排查

```
{指出具体现象} {给出具体文件路径}

你没发现全部都重复了吗 这是bug 想办法修复下
很显然 你设立的唯一id被绕过去了
```

**为什么有效**：给出具体证据（文件列表）+ 自己的初步判断（"唯一 ID 被绕过"）帮助 AI 缩小排查范围。

## 4. 需求澄清 prompt

**场景**：AI 做了不符合预期的实现，重新明确需求

```
所有的按键有中文解释的写中文解释 英文作为括号内容
接下来是每个页面的建议...
```

**为什么有效**：逐页逐功能给出明确期望，而不是笼统说"优化一下"。

## 5. 冷启动测试 prompt

**场景**：验证修复是否真的生效

```
模拟 BUG-001：在临时数据库中不创建 documents 表，
然后调用 _init_and_ensure_columns，确认它自动创建表并添加列
```

**为什么有效**：给出了精确的测试步骤和预期结果。

## 6. UI 原型验证 prompt

**场景**：在写正式代码前先做 UI mockup

```
先做一版模拟网站 只是做前端，后端不做
让我看看效果，单独放在一个文件夹里面
```

**为什么有效**：用假数据和纯 UI 快速验证设计思路，避免写完后端才发现 UI 方向错了。

## 7. Git 保存 checkpoint

**场景**：在关键节点前要求 AI 保存进度

```
git保存之后执行{plan}。执行过程中在关键节点到来前多git保存
确保能够随时回退进度。尽可能少打扰我。
```

**为什么有效**：给 AI 明确的 checkpoint 策略+"少打扰"的约束。

## 8. 复盘点 prompt

**场景**：项目结束后整理复盘

```
将我们的代码书写过程 和代码debug过程写出报告，
方便之后项目复习
```

**为什么有效**：要求"记录过程"而非"总结功能"，得到的是时序性的复盘材料。

---

## 通用原则

1. **给出具体文件路径和行号**，不是模糊描述
2. **明确角色**（测试工程师 / 架构师 / 代码审查者）
3. **给出证据**（报错信息 / 文件列表 / 截图），不是只给结论
4. **设置可验证的验收标准**（"搜索 ai 应该返回 14 条结果"）
5. **分步骤、分阶段交付**（先 mockup → 再真实后端 → 最后打磨）
