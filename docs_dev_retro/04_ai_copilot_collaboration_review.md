# 04 — AI Copilot 协作复盘

**用途**：诚实评估 Claude Code 在 KB Console 开发中的实际表现——帮了什么忙，帮了什么倒忙。

**读者**：自己 / 想了解 AI Copilot 真实能力边界的开发者。

**方法论**：每一个评价都附带具体例子和对话上下文，不泛泛而谈。

---

## 一、Copilot 真正有用的地方

### 1. 大规模代码生成：一次写出 80% 能用的骨架

**例子**：v2 重写时，我描述了 6 组导航 + 9 个页面的需求和 mockup 参考，Copilot 一次性生成了 ~750 行的 `streamlit_app.py` 和 ~580 行 `ui_helpers.py`。虽然后续有几轮 bug 修复，但骨架是对的——导航结构、页面组织、异步任务框架都无需推翻。

**为什么有用**：这类"有明确模式但量大"的代码，人写要 2-3 小时，Copilot 5 分钟出初稿。关键是 **mockup 已经验证了设计方向**，Copilot 做的是"把已验证的设计翻译成代码"。

**有效的前提**：在你给它看 mockup 之前，它不知道你想要什么。给了 mockup 之后，输出质量跃升。

---

### 2. 根因分析：顺着调用链追溯到设计缺陷

**例子**：文件重复问题。用户指出 `_2` 后缀文件后，我让 Copilot 从现象开始逆推：
1. `_unique_path` 为什么产生 `_2`？→ 文件已存在
2. 为什么文件已存在？→ mtime 去重失败
3. 为什么 mtime 去重失败？→ 浮点精度问题 ✓
4. 还有没有其他原因？→ `fingerprint_sha256` 来自 `sampled_text`
5. `sampled_text` 是怎么来的？→ `sampler.random_segments: 3`
6. 随机采样 → SHA 不固定 → 文件名每次都不同 → 整个去重体系建立在非确定性数据上 ✓

**为什么有用**：这种 5 层追溯的 RCA 是人也能做的，但 Copilot 顺着代码调用链跳转比人快得多——从 `_unique_path` → `weekly_organize` → `database.process_file` → `_row_values` → `sampler`，30 秒完成。

**有效的前提**：人必须指出"这里有问题"，Copilot 负责追溯。不能期望它主动发现"这个设计有隐患"。

---

### 3. 测试用例生成：一次性覆盖 39 个函数

**例子**：`tests/test_gui_backend.py` 覆盖了 GUI 调用的所有后端函数（find_idea、token_budget、get_dashboard_enriched、fetch_folder_docs 等），39 个测试用例，一次生成基本可用。

**为什么有用**：写测试是"有明确格式但枯燥"的工作——给 Copilot 函数签名 + 预期行为，它生成测试代码。人在写"验证 pipeline 不崩"这种测试时特别容易漏边界 case，Copilot 会补上（空查询、不存在的词、越界路径）。

---

### 4. 同类问题扫描：11 个函数一个不漏

**例子**：BUG-001 修完后，我让 Copilot "grep 所有调用 `_ensure_doc_columns` 的地方"，它立刻列出 11 个函数，标注哪些已经调了 `KBDatabase.init()`、哪些没调。这种查找+比对的工作，人做要 10 分钟，Copilot 5 秒。

**为什么有用**：Copilot 不会"觉得麻烦就跳过"——它会老老实实把每个匹配行列出来。

---

### 5. UI 原型快速验证

**例子**：在写 v2 代码之前，Copilot 用纯假数据做了一个 Streamlit mockup（`ui-mockup/mock_app.py`）。用户在浏览器里看了交互流程后给了关键反馈（"交易分析应该通用化"），避免了在错误方向上写几百行代码。

**为什么有用**：从"需求讨论"到"可视化原型"只需要一次 prompt。这个循环如果人来做（即使是用 Streamlit），至少 1-2 小时。

---

### 6. 文档结构化：一次生成完整骨架

**例子**：用户要求"写一套复盘文档"，Copilot 一次性生成了 10+2 个文件的完整骨架，每个文件包含用途说明、目标读者、章节标题、填充指南。

**为什么有用**：结构化文档的关键是"不遗漏"。Copilot 从一个想法（"做项目复盘"）自动展开为完整的文档体系（时间线 + bug 手册 + 需求演进 + 协作复盘 + 检查清单 + prompt 模板 + blog 版 + 附录）。这种"从一个点看到一个面"的结构化能力，是 Copilot 最被低估的价值。

---

## 二、Copilot 容易帮倒忙的地方

### 1. 测试环境≠运行环境：最危险的假阳性

**例子**：整个 BUG-009 的排查过程。

Copilot 的所有测试都 `cd kb_tool` 然后跑。`find_idea('ai')` → 14 条结果 → "后端正常"。

用户用 GUI发现搜不到任何东西。Copilot 在错误方向上排查了 1 小时——检查 `find_idea` 代码、FTS5 表结构、chunk 数据——全是正常的。

真正的问题是：GUI 从项目根启动，config 中的 `"./kb_out/kb.sqlite3"` 解析到 `root/kb_out/kb.sqlite3`（0 条文档的空库）。Copilot 从 `kb_tool/` 测试，解析到 `kb_tool/kb_out/kb.sqlite3`（正确的库）。**同一个代码，不同工作目录，读到不同数据。**

**为什么这是 Copilot 的典型失败模式**：Copilot 不会主动质疑"我的测试环境和用户的使用环境一样吗"。它会在给定的工作目录下验证，然后自信地报告"正常"——这种自信的假阳性比直接报错危险 100 倍。

**应该怎么做**：人在 Copilot 说"已完成"之后，必须从用户的实际使用路径验证一次。不要信任 Copilot 的测试结果，除非你确认测试方式和用户操作方式完全一致。

---

### 2. "已完成"三个字是最危险的输出

**例子**（不只一次）：
- Copilot 修完 BUG-009（路径绝对化）后说"修复完成，搜索正常"。用户测试 → 还是搜不到。
- Copilot 修完 BUG-011（子进程缓冲）后说"修复完成"。用户启动任务 → 还是卡在"子进程启动中"。
- Copilot 多次在 git commit message 中写"验证通过"但实际从没跑过验证命令。

**为什么这是 Copilot 的典型失败模式**：Copilot 的"完成"判断标准是"我改了代码"——但用户的判断标准是"改了之后能用"。这两个标准之间差了一个**真实验证**的步骤。Copilot 天然倾向于跳过验证，因为它"知道"代码逻辑是对的。

**应该怎么做**：永远不要接受 Copilot 的"已完成"。要求它贴出验证命令和关键输出。如果它贴不出来，就是没验证。本项目后来加了这个规则（Vibe Coding Rules #12）。

---

### 3. 缺乏"这个设计有隐患"的主动性

**例子**：BUG-008c（SHA 随机采样）。

`database.py` line 340 写了 `fingerprint_sha256 = self._sha256_text(sampled)`。Copilot 看到这行代码无数次——在代码审查、bug 修复、功能开发中——但从没主动说"这里用采样文本算 SHA 可能有问题"。

直到用户发现了重复文件，人手动追溯调用链，才发现这个设计缺陷。Copilot 能追溯问题，但不能**预判**问题。

**为什么这是 Copilot 的典型失败模式**：Copilot 的注意力由 prompt 驱动。人没问"这个设计有什么隐患"，Copilot 就不会去检查。它不会像有经验的开发者那样，看到 `sampled_text` + `sha256` 的组合就本能地皱眉头。

**应该怎么做**：关键模块（数据指纹、路径解析、ID 生成、并发控制）需要人主动审查。不要假设 Copilot 会提醒你"这里可能出问题"。在项目初期明确要求 Copilot "对这个模块做一次设计审查"。

---

### 4. 过度工程化：复杂的方案往往是人一句话纠正的

**例子**：
- **Embedding vs Agentic Search**：用户说"搜索不应该只是关键词"。Copilot 的第一反应是引入向量数据库（ChromaDB/LanceDB）+ Embedding 模型（bge-m3）。用户说"无论是查wiki还是embedding还是agentic search都好"——Copilot 才意识到已有的 Agent + MCP 工具链就够了。
- **递归 Bundle 嵌套**：超出 100 万字时，Copilot 第一版实现是 `render_bundle_markdown` 递归调用自己。用户说"每一百万字压缩，最后总结"——1 句话就把复杂的递归设计推翻，改成简单的"split → 并发 compress → synthesize"。
- **文件夹选择器**：Copilot 第一版是列出桌面所有子文件夹的 checkbox 列表（几十个）。用户说"就和下载文件选定目录一样"——Copilot 才写出 PowerShell 调 FolderBrowserDialog 的方案。

**为什么这是 Copilot 的典型失败模式**：Copilot 的"方案搜索空间"偏技术化——它会优先选择"引入新库/新技术栈"的方案，而不是"复用现有基础设施"。人也一样，但人可以一句话纠正方向。关键是**在 Copilot 开始写复杂方案之前先让它说清楚"你打算怎么做"，然后人判断方向对不对。**

---

### 5. 代码细节错误：缺 import、用错 API、typo

**例子**：
- BUG-005：`st.script_run_ctx` 不存在。正确是 `from streamlit.runtime.scriptrunner import get_script_run_ctx`
- BUG-006：用了 `json.dumps()` 但没 `import json`
- `ui-mockup/mock_app.py`：`page_layout="wide"` 应该是 `layout="wide"` → 启动直接崩溃

**为什么这是 Copilot 的典型失败模式**：这类错误人一眼能看出来，但 Copilot 不会。它的代码在"看起来正确"和"实际能跑"之间有一个 gap。人必须跑一遍语法检查。

**应该怎么做**：每次 Copilot 生成/修改代码后，人（或自动化）必须跑 `py_compile.compile()` 或等效的语法/导入检查。本项目在 Phase 3 之后形成习惯——每次改完立刻跑语法检查。

---

### 6. 串行思维：默认 for 循环，不主动并发

**例子**：`compress_and_synthesize` 分批压缩时，Copilot 的第一版实现是 `for chunk in chunks: llm_call()` ——串行。3 批 × 30 秒 = 90 秒。

用户问"这个是并发吧 不是的话改过来"。Copilot 才改成 `ThreadPoolExecutor`。

**为什么这是 Copilot 的典型失败模式**：Copilot 默认写串行代码。它不会主动判断"这些操作互不依赖、可以并发"。人的经验——"LLM API 是独立 HTTP 请求，天然并发"——Copilot 没有。

**应该怎么做**：看到 for 循环里调 API/网络/文件 I/O 时，主动问 Copilot："这些操作依赖前一步的结果吗？不依赖的话改成并发。"

---

### 7. 修改后不检查副作用

**例子**：修 BUG-008（文件去重）时，Copilot 在 `weekly_organize` 里加了"文件已存在则跳过复制"的逻辑。但没删除临时 inbox 文件的 DB 记录 → 每次跳过复制就留下一条孤儿行。虽然不影响功能，但会在 DB 里累积垃圾数据。

另外，多次修改后没有重新运行全量测试 → 修复 A 破坏了 B 的风险始终存在。

**为什么这是 Copilot 的典型失败模式**：Copilot 的注意力局限在当前函数。它不会主动想"我改了这个函数，哪些地方调用了它？会不会受影响？"

**应该怎么做**：要求 Copilot 在修改函数后，用 grep 列出所有调用方，逐个确认不受影响。修改后跑全量测试，不要只跑改了的那一个。

---

## 总结：Copilot 的"能力边界"

| 任务类型 | 评分 | 关键前提 |
|----------|:---:|------|
| 大规模 CRUD/UI 代码 | ⭐⭐⭐⭐ | 人已验证设计方向（有 mockup） |
| RCA 根因追溯 | ⭐⭐⭐⭐ | 人指出"这里有问题" |
| 测试用例生成 | ⭐⭐⭐⭐ | 给出函数签名和预期行为 |
| 同类问题扫描 | ⭐⭐⭐⭐⭐ | 几乎没有前提 |
| 文档结构化 | ⭐⭐⭐⭐⭐ | 几乎没有前提 |
| 环境感知（cwd/路径） | ⭐ | 人必须显式确认 |
| 验证"已完成" | ⭐ | 绝对不要信，自己跑命令 |
| 主动发现设计隐患 | ⭐ | 人必须主动审查关键模块 |
| 方案选择（简单 vs 复杂） | ⭐⭐ | 人必须在写代码前审查方案 |
| 代码细节（import/API） | ⭐⭐ | 每次跑语法检查 |
| 并发优化 | ⭐ | 人需要主动提出 |
| 修改副作用检查 | ⭐⭐ | 人需要要求 grep + 全量测试 |

---

## 最佳协作模式（从本项目提炼）

```
人：明确需求 + 给出 mockup/具体例子 + 审查方案方向
     ↓
Copilot：生成代码骨架 + 写测试 + 追溯根因 + 扫描同类问题
     ↓
人：从用户实际路径验证 + 语法检查 + 跑全量测试
     ↓
Copilot：根据验证结果修复
     ↓
人：再次验证 → 接受
```

**核心原则**：Copilot 负责"广度"（写出所有代码、扫描所有文件），人负责"深度"（判断方向对不对、验证是不是真的能用）。人把 Copilot 当成一个"非常快但不会质疑你的初级工程师"来管理，这个心态最接近实际体验。
